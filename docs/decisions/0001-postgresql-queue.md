# ADR 0001: Procrastinate для очереди обработки

Статус: выбран для следующей реализации; проверка этапа 1 выполнена.
Версия эксперимента: Procrastinate 3.11.0, Python 3.12, psycopg 3, SQLAlchemy 2,
PostgreSQL 17. Точная установка зафиксирована uv.lock и группой experiments.

## Решение

Использовать Procrastinate в той же PostgreSQL, сохранив отдельный процесс worker.
Постановка задания выполняется через `configure_task(..., connection=raw).defer(...)`,
где `raw = session.connection().connection.driver_connection` принадлежит текущей
SQLAlchemy Session. Управляет commit/rollback только прикладная транзакция.
Отдельная постановка после commit видео и отдельный commit на другом соединении
не допускаются: они оставляют окно потери задания.

Библиотека пока находится только в группе experiments; производственный образ
и Alembic не получают очередь до этапов загрузки/worker. Эксперимент использует
маленькую таблицу `stage1_probe_videos`, которая не является моделью videos.

## Что проверено

- До commit другая сессия не видит задание.
- Rollback убирает и предметную запись, и задание.
- Commit сохраняет обе записи, worker выполняет задание.
- Worker принудительно завершён через SIGKILL после начала задания.
- Задание остаётся doing; просроченный heartbeat позволяет найти его через
  публичный `job_manager.get_stalled_jobs`.
- Явный `retry_job_by_id_async` возвращает его в очередь; новый worker завершает
  работу. Счётчик выполнения — 2: это at least once, не exactly once.

## Обязательные условия производственного использования

1. Нужен периодический recovery-проход с ограниченными повторами и журналом.
   Одного запуска нового worker недостаточно: библиотека удаляет старую запись
   worker, но это не равно повторной постановке всех doing-заданий.
2. Сбой heartbeat может означать живой старый процесс. В домене видео нужен
   собственный attempt/generation token, уникальные пути результатов и условная
   публикация. Библиотечная очередь не заменяет защиту устаревшего результата.
3. Задания и очистка идемпотентны; удаление видео и отмена публикации проверяются
   транзакционно. Нельзя обещать однократный запуск FFmpeg.
4. В payload только video_id и технический идентификатор попытки. Приватные
   названия, пути, cookie и токены туда не помещаются: библиотека может логировать args.
5. Схема и обновления библиотеки устанавливаются контролируемыми миграциями
   зафиксированной версии. `apply_schema()` не вызывается при каждом старте API.
6. При внедрении этапа 4 задача не создаёт новую самописную очередь рядом с
   библиотечной. Логические поля jobs из архитектуры адаптируются к её схеме;
   domain attempt token остаётся ответственностью videos.

Проверка не покрывает обработку настоящего видео, конкурирующих живых устаревших
workers, работу с файлами и обновление версии библиотеки. Это проверки этапа 4.

## Альтернативы

- Собственная очередь: сохраняет транзакционность, но требует поддержки scheduler,
  worker lifecycle и повторов. После успешной проверки библиотеки это лишняя работа.
- Celery/Redis: добавляет сервис и отдельное решение согласованной доставки
  между PostgreSQL и брокером. Для текущего MVP преимущества не показаны.

## Повторение эксперимента

Нужна **новая пустая** БД с именем, оканчивающимся на `_probe`. Настройки подключения
берутся из обычных переменных приложения, без печати значений паролей.

```bash
uv sync --locked --group experiments
# Создайте отдельную пустую stage1_queue_probe; не запускайте миграции приложения в ней.
POSTGRES_DB=stage1_queue_probe uv run --locked --group experiments python experiments/queue_probe.py
```

Скрипт отказывается устанавливать схему в непустую БД и в БД без суффикса.
После проверки тестовая БД удаляется отдельно. CI повторяет эксперимент в
отдельной PostgreSQL service database. К текущей production-БД эксперимент не подключают.
