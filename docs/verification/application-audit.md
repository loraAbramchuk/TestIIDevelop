## Подтверждённые замечания

Все пять замечаний имеют приоритет P2: стоит исправить до приёмки интерфейса.
Таймауты и повреждённый ответ ниже моделировались в браузере специально;
штатный сервер в обычных сценариях таких ответов не возвращал.

### A1. Подготовка загрузки зависает без доступной отмены

В [upload.js](../../app/static/upload.js) отдельный запрос CSRF перед отправкой
файла использует `fetch` без AbortController/таймаута. Это не обработчик входа:
исправления авторизации из предыдущей ветки здесь не применяются.

Воспроизведение: открыть карточку в состоянии uploading, выбрать файл и
задержать `/api/auth/csrf`. Спустя более 16 секунд остаётся «Подготовка загрузки…»,
выбор файла и отправка заблокированы, ошибки нет, кнопка отмены ещё скрыта.

Нужно ограничить время подготовки, возвращать управление и сохранять выбранный
файл/метаданные. Передача большого файла должна иметь собственные правила
ожидания; короткий таймаут подготовки не следует применять ко всей загрузке.

### A2. Обсуждение, плейлист и разрешения остаются заблокированы

Собственные GET-функции в [interactions.js](../../app/static/interactions.js),
[playlists.js](../../app/static/playlists.js) и [videos.js](../../app/static/videos.js)
обходят уже существующий ограниченный по времени `apiRead`.

Воспроизведены три случая зависшего ответа:

- `/api/videos/{id}/likes`: обновление обсуждения и отправка комментария
  остаются disabled; ошибки нет;
- `/api/playlists/{id}` при обновлении: отключены обновление и редактирование
  названия, ошибки нет;
- `/api/videos/{id}/grants`: отключены обновление и поле получателя доступа,
  ошибки нет.

Наблюдение выполнено после более 16 секунд. У Nginx есть серверные таймауты,
но они не заменяют ограничение ожидания на клиенте при обрыве/зависании сети
между браузером и прокси. Нужно ограничивать также чтение тела ответа,
восстанавливать кнопки и давать безопасную повторную загрузку состояния.

### A3. Неполный ответ на комментарий ошибочно считается успехом

В [interactions.js](../../app/static/interactions.js) вызов POST комментария
не передаёт валидатор результата в `apiRequest`. [api.js](../../app/static/api.js)
в этом случае проверяет только то, что ответ — JSON-объект.

Воспроизведение: подменить ответ POST на HTTP 201 с `{}`, не отправляя запрос
серверу. Поле комментария очищается, появляется «Комментарий добавлен.»,
хотя повторный GET подтверждает отсутствие этого комментария.

Нужно проверять обязательные поля результата до очистки черновика и сообщения
об успехе. При неоднозначном результате сохранять текст и предлагать проверить
обсуждение; автоматически повторять POST нельзя.

### A4. Ошибочные ссылки просмотра и студии показывают JSON

В [application.py](../../app/application.py) HTML-обработчик ошибок валидации
не включает `/watch/` и `/studio`. [videos/pages.py](../../app/videos/pages.py)
не переводит ошибку доступа/отсутствия карточки студии в HTML-страницу.

Подтверждено настоящими HTTP-запросами:

| Адрес | Результат |
| --- | --- |
| `/watch/not-a-uuid` | 422, JSON без навигации |
| `/studio/videos/not-a-uuid` | 422, JSON без навигации |
| `/studio?limit=abc` | 422, JSON без навигации |
| `/studio/videos/00000000-0000-0000-0000-000000000001` | 404, JSON без навигации |

Для сравнения, `/channels/not-a-uuid` уже возвращает оформленную HTML-ошибку.
Нужно унифицировать страницы, сохранив исходные HTTP-статусы и JSON для API.

### A5. Мобильная ссылка создания видео не имеет доступного имени

В [base.html](../../app/templates/base.html) у `.create-link` нет `aria-label`.
В [styles.css](../../app/static/styles.css) при ширине до 700 px текст «Создать»
скрывается через `display: none`, а SVG скрыт от экранного диктора.

axe-core 4.11.0 обнаружил `link-name` на всех 11 проверенных страницах при
390 px. Дополнительная проверка роли/имени подтверждает: ссылка с именем
«Создать» отсутствует на 320/390/700 px и присутствует на 701/1440 px.
Нужно дать ссылке постоянное доступное имя, например «Загрузить видео».
