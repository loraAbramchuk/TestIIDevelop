## Что реализовано

- Регистрация остаётся открытой. Новый аккаунт получает сессию, но действия
  с контентом и служебные действия требуют подтверждённого email.
- Подтверждение, повтор письма, запрос восстановления и новый пароль:
  четыре API-операции, экраны, CSRF и ограничения частоты. Ссылки одноразовые;
  срок подтверждения 60 минут, восстановления 30 минут. Сброс отзывает все
  прежние сессии и не выполняет автоматический вход.
- SMTP через отдельного потребителя существующей Procrastinate/PostgreSQL
  очереди. Сетевой запрос не блокирует HTTP и не держит транзакцию БД.
  Повтор после неопределённого SMTP-ответа может доставить то же письмо ещё раз;
  ссылку можно использовать только один раз.
- Миграция 0012 сохраняет пользователей, пароли, каналы и сессии. Существующие
  адреса не подтверждаются автоматически. CLI-администратор создаётся доверенной
  локальной командой. Обновление и почта: [email.md](../email.md).
- По результатам аварийных проверок FFmpeg/ffprobe ограничены также
  `-cpucount 1`: внутренние автоматические пулы не ориентируются на число CPU
  хоста вопреки лимитам worker. Нехватка временных ресурсов отделена от
  недопустимого видео и допускает ограниченный повтор.
- Зафиксированы политика резервных копий 30 дней, release notes 0.2.0 и
  проверка готовности, которая отклоняет устаревший отпечаток исходников.

## Измерения

Условия: host Python 3.12 и FFmpeg 7.1, отдельные PostgreSQL 17 и Nginx,
loopback, тёплый кэш. Worker закреплён за одним CPU; HTTP работает без affinity,
`PROCESSING_CONCURRENCY=1`. Это не тест целевой VM или публичной сети.
На стенде лимит файла уменьшен до 64 МиБ; образцы H.264/AAC, 30 fps.

### Начальные настройки сервера

Для пилота разумная отправная точка — 4 vCPU, 8 ГиБ RAM и SSD. Это рекомендация
для дальнейшего замера, а не подтверждённый минимум RAM: пиковое потребление
памяти и производительность конкретного хоста здесь не измерялись.
Сохранить один процесс обработки, два upload-слота на автора и четыре всего;
увеличивать параллелизм только после замера очереди, RSS, диска и HTTP p95.
Текущие пределы: файл 1 ГиБ, автор 10 ГиБ, общий media budget 100 ГиБ,
резерв свободного места минимум 2 ГиБ, очередь до 100 заданий. Эти квоты
настраиваются; они не заменяют физический запас диска.

Ёмкость SSD должна покрывать media, PostgreSQL, резерв обработки, образы,
временный согласованный snapshot, зашифрованный архив и сохраняемые локальные
копии. При заполненных 100 ГиБ media только данные + snapshot + один архив
могут потребовать около 300 ГиБ до учёта БД и остальных файлов. Число локальных
копий и внешний объём рассчитать отдельно. Предупреждение по диску должно
срабатывать раньше жёсткого резерва, с запасом на очередную копию.

Нужный внешний канал примерно равен сумме битрейтов зрителей плюс запас:
например, 20 потоков по 10 Мбит/с требуют более 200 Мбит/с исходящего канала.
Локальные результаты нельзя переносить на интернет-канал сервера.

## Сбои и журналы

Все перечисленные сценарии прошли на синтетических данных:

- SIGKILL worker во время настоящего FFmpeg/ffprobe: дочерний процесс завершён,
  просроченная аренда восстановлена, повтор довёл видео до ready.
- SIGKILL после приёма SMTP DATA до ACK: восстановлено задание, повторена
  та же ссылка; первая активация 200, повторная 400.
- Остановка только изолированного PostgreSQL: live 200, ready/API 503;
  после запуска БД доступ и хеш файла сохранены.
- Завышенный резерв свободного места: запись 507, просмотр работает.
  Реально read-only каталоги: запись деградирует, чтение готовых файлов работает.
  Физический ENOSPC основного диска намеренно не создавался.
- Удаление во время обработки: новые чтения сразу закрыты, старое задание
  не публикует результат, фоновая очистка выполняется.
- В семи журналах не найдены 91 проверенный секретный маркер: пароли,
  сессии/CSRF, ключ подписи, полные ссылки, email, приватное название и
  внутренние ключи файлов. Операторские ID/обычные исходные URL могут
  присутствовать. Приватные fixture context и SMTP inbox специально содержат
  синтетические ссылки и хранятся с правами 0600, в Git не входят.

Политика копий — **до 30 дней**, включая удалённое содержимое в копиях.
`BACKUP_KEEP_LOCAL` ограничивает количество, возраст применяет оператор на
локальном и внешнем хранилище. Существующие архивы не удалялись. Доступ к видео
закрывается сразу, физическая очистка асинхронна; автоматический TTL
soft-deleted SQL-метаданных и аудита не задавался.

## Воспроизведение проверки

Нужны установленные зависимости проекта, Docker, FFmpeg/ffprobe, taskset,
Node.js с Playwright и системный `/usr/bin/chromium`. Нужны Docker-образы
`postgres:17-bookworm` и заранее собранный `video-platform-web:local`
(`docker compose build web` на настроенном checkout). Требуется не менее 4 ГиБ свободного места;
порты 15434/8014/8099/1026 должны быть свободны. Выполнять из корня checkout:

```bash
uv run --locked python experiments/mvp_release_probe.py --output /tmp/mvp-stage12-new-run
uv run --locked python scripts/release_check.py /tmp/mvp-stage12-new-run/evidence.json
uv run --locked python scripts/release_check.py /tmp/mvp-stage12-new-run/evidence.json --public
```

Выходной каталог обязан быть новым. Стенд создаёт собственные помеченные
контейнеры/volume, БД, media и локальный SMTP, очищает их в `finally`;
отчёты остаются в приватном каталоге. Основные `.env`, БД, media и backup
не меняет. В тестовом host/Docker стенде права чтения синтетических media
адаптируются под разные UID; это не изменение production-политики владельца.
Браузер запускается самим стендом. `--skip-tests` и `--skip-faults` оставляют
проверки unrun и не дают пройти локальную приёмку.

Итоговый прогон: `/tmp/stage12-complete/evidence.json`, тесты
`/tmp/stage12-complete/tests.log`; дополнительные проверки Swagger
`/tmp/stage12-swagger.log`, миграции `/tmp/stage12-migration-result.log`.
Команда готовности сверяет SHA-256 дерева исходников/конфигурации/тестов
с протоколом; после их изменения нужен новый прогон. Первая команда проверки
готовности возвращает **0**, с `--public` сейчас ожидаемо **1**.
