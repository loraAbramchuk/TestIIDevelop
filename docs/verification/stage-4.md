# Этап 4: обработка видео и восстановление worker

Ветка `feature/stage-4-video-processing` создана от `work` на `bc3997b`.
Это результаты локальной облачной среды; GitHub Actions здесь не подтверждается.

## Реализовано

- `app/processing`: Linux launcher, ограниченные subprocesses, проверка профиля,
  подготовка файлов, доменные поколения/аренды, worker и health CLI.
- Миграция 0006: processing_runs и processing_workers, счётчики обработки/recovery,
  current_run_id и ссылки/размеры готового MP4/JPEG. Прежний payload очереди не менялся.
- Procrastinate 3.11.0 по-прежнему выдаёт задания videos.process; второй очереди
  нет. ProcessingRun отвечает только за исполнение, fencing и уборку файлов.
- Worker проверяет ffprobe: MP4 brand, одну H.264-дорожку, progressive yuv420p,
  Baseline/Main/High до 4.2, размеры/частоту/длительность, отсутствие либо одну
  AAC-LC mono/stereo 44.1/48 kHz. Лишние дорожки, 10-bit/HEVC и другие профили
  отклоняются; перекодирования несовместимых кодеков нет.
- MP4 создаётся stream-copy с faststart. После проверки длительности и полного
  декодирования создаётся JPEG до 640 px. Файлы fsync/rename предшествуют транзакции
  ready, ключей, размеров, длительности и состояния stored. Видимость/grants/
  модерация не изменяются; deleted_at и актуальность поколения проверяются заново.
- Каждый запуск имеет UUID, аренду и отдельный каталог. Heartbeat обновляется
  временем БД после блокировки строки. Старый запуск не публикует и не портит
  новое поколение. Физические flock ограничивают писателей одного исходника и
  общее число media-процессов даже при нескольких worker на одном сервере.
- После SIGKILL child получает SIGKILL через PR_SET_PDEATHSIG; унаследованные
  блокировки также не допускают параллельного писателя, пока child ещё жив.
- Подтверждение/retry библиотечного задания проверяют worker_id **и attempts**
  в одной CTE-транзакции. Старый ack не затрагивает повтор даже в том же worker.
- Maintenance возвращает прерванные/временно неудачные задания в библиотечную
  очередь с ограниченным recovery-бюджетом. После сбоя между ready и ack повтор
  подтверждает задание без повторной подготовки. Ошибки профиля/декодирования/
  бюджетов терминальные, storage/DB — временные. До 3 фактических media-запусков;
  ожидание физического слота не выполняет media и не увеличивает этот счётчик.
- Перед обработкой повторно проверяется свободный запас диска с учётом ещё не
  материализованных резервов. Сумма производных ограничена **записанным резервом**,
  даже если настройки поменялись после загрузки. После ready учитывается фактический
  размер source+MP4+JPEG; при ошибке — освобождение после успешного unlink.
- Compose: отдельный worker, CPU=1, memory=2 GiB, pids_limit=64, read-only root,
  ограниченный tmpfs, non-root, cap_drop=ALL/no-new-privileges. В child — минимальное
  окружение без конфигурации БД, RLIMIT_AS=768 MiB, CPU/file-size caps, -threads 1,
  filter_threads=1, max_alloc=64 MiB. Разрешены file-протокол/MOV demuxer, внешние
  data references выключены. Общий deadline 900s, probe 30s, stdout/stderr ограничен.
- `/health/ready` проверяет схему/чтение, включая новые таблицы/колонки, без требования
  работающего worker. Diagnostics показывает свежий worker heartbeat. При остановке
  worker HTTP остаётся готов, приём разрешён до заполнения квоты/очереди.

## Результаты

| Проверка | Результат |
| --- | --- |
| Полный pytest с PostgreSQL 17 и FFmpeg | **148 passed**, прежнее предупреждение Starlette TestClient/httpx2 |
| Реальные H.264/AAC и H.264 без аудио | ready, размеры/длительность, JPEG и moov перед mdat; исходник сохранён, повтор задания не меняет результат |
| Неверный профиль | 10-bit и не-видео дают failed с безопасным кодом; source/частичные результаты удаляются с освобождением квоты |
| Политика и бюджеты | Несовместимые дорожки/кодеки, interlaced, attached picture, AAC channels/rate, размеры/fps/duration/NaN/Infinity; таймаут, потеря аренды, ограничение размера файла, слоты, ошибки storage |
| Повторы | Реальная библиотечная очередь повторяет временный ENOSPC и завершает следующий запуск; фактические обработки ограничены |
| Fencing | Истёкшая аренда, старое поколение, устаревшие finish/retry из другого и того же worker не меняют актуальное исполнение |
| Удаление во время обработки | Soft-delete в тесте запрещает публикацию; cleanup удаляет все результаты и исходник. Публичного DELETE endpoint ещё нет |
| Сбой после публикации | Recovery оставляет ready/ключи, повторяет только ack; media-запуск остаётся один |
| Реальный SIGKILL | Worker убит во время FFmpeg/ffprobe; child завершён, слот освобождён, просроченное поколение fenced, повтор достигает ready, source сохранён, job=succeeded |
| Миграции | 0005 → 0006 → 0005 → 0006 на отдельной БД: users/sessions/counters/grants/исходник/старое задание сохранены. Старое задание после upgrade достигает ready; alembic check без расхождений |
| Chromium 156.0.8078.79 через Nginx | Upload → ready, private metadata 404 гостю, 10-bit → failed, повтор совместимого файла в ту же карточку → ready; мобильная ширина 390px, без ошибок JS |
| Swagger | 17 операций, Try it out возвращает живой ответ; внешние запросы заблокированы, ошибок нет |
| Compose | Обычный start.sh собирает образ с FFmpeg, применяет 0006; app/web/db/worker healthy, maintenance запущен, processing=ok |
| Ruff / формат / контракт | Пройдены; CI устанавливает FFmpeg для фактических media-тестов |

SIGKILL-проверка использовала повторённый 100-секундный клип 320×180 и настоящую
аренду 4s/heartbeat 1s/retry 1s для быстрого восстановления. Browser-проверка —
маленькие реальные 2-секундные файлы. Лимит 1 GiB, двухчасовое Full HD видео,
нагрузочная вместимость, power-loss, сетевые FS, fuzzing и Firefox/Safari в этом
этапе не испытывались. Гарантии flock/PDEATHSIG относятся к одному Linux-серверу
с общим локальным POSIX-volume. Живой процесс, удерживающий блокировку, не удаляется
уборщиком; после его остановки/выхода очистка и повтор продолжаются.
