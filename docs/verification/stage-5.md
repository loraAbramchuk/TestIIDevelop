# Этап 5: защищённое воспроизведение и удаление

Ветка `feature/stage-5-protected-playback` создана от `work` на `6094432`.
Это проверка локальной облачной среды; прохождение GitHub Actions не заявляется.

## Реализация

- GET/HEAD stream и thumbnail используют тот же SQL-фильтр `viewable_by`, что
  метаданные. Проверяются ready, visible, отсутствие удаления и public/owner/grant;
  роли admin/moderator не обходят политику. ACL выполняется до обращения к файлам.
- Приложение допускает только immutable-ключи processing/UUID/playback.mp4 и
  thumbnail.jpg. Проверяются каталоги/файл без перехода по symlink, регулярный тип
  и сохранённый размер. Отсутствующий/изменённый файл после ACL даёт безопасный 503.
  Приложение не читает видео в память и не реализует второй механизм Range.
- Nginx получает X-Accel-Redirect на internal location. Источники, временные файлы
  и прямые пути недоступны. Nginx читает media read-only, worker UID совпадает с
  его media-пользователем (10001), закрытые права 0700/0600 сохранены.
- Nginx отдаёт Content-Type, Content-Length, Accept-Ranges, 206/416/Content-Range,
  HEAD без тела. max_ranges=1: несколько диапазонов дают полный ответ 200.
  File cache и ETag выключены; Cache-Control: private, no-store и Vary: Cookie.
  Условный запрос может получить 304 только после ACL. После отзыва/удаления
  запрос с Range/If-None-Match/If-Modified-Since получает 404.
- `/watch/{id}`: native-плеер, защищённое превью, название, описание и переход
  владельца к управлению. Поля HTML экранируются. Недоступное видео даёт одинаковую
  HTML-страницу 404 без метаданных. Есть ссылки на просмотр после ready и в студии.
- DELETE доступен владельцу с CSRF и лимитом записи. Одна транзакция ставит
  tombstone, отменяет/abort-ит библиотечные задания, снимает аренды поколений,
  записывает cleanup в upload_attempts. Новый просмотр запрещён сразу; места
  в квоте до фактической очистки не прибавляется. Старые публикации fenced.
- Используется существующий durable-журнал cleanup и отдельный maintenance;
  новые таблицы и миграции не добавлены. При активном flock очистка откладывается,
  а после рестарта повторяется. Повтор DELETE владельцем — 204, чужим — 404.
- UI удаления запрашивает подтверждение, после успеха возвращает в «Мои видео».

## Исправления после повторной проверки

- После потери ответа 202 сверка processing возобновляет автоопрос; ready
  показывает ссылку просмотра без ручного обновления. Принятый файл имеет 100%
  передачи независимо от потерянного ответа браузеру.
- Ошибки действия загрузки отделены от ошибок обработки. Ответ 429 сохраняется
  и при uploading, и при повторе failed, включая ручную проверку статуса;
  после успешного повтора сообщение очищается. Ответ 507 проверен имитацией
  квоты на клиентском пути без заполнения диска.
- Выдача/отзыв доступа обновляют только список grants через GET API. Название,
  описание и выбранная видимость не меняются и не сохраняются автоматически.
  Повтор grant не создаёт дубль, refresh сохраняет limit/cursor и корректную
  следующую страницу. При сбое GET после успешной мутации результат действия
  показан отдельно; кнопка обновления восстанавливает список без повторной записи.
- Регрессии: experiments/upload_recovery_browser_probe.cjs на отдельном
  stage5-verify. Проверены реальная потеря ответа, два receiving PUT и отказ 429,
  повтор в ту же карточку, имитация 507/503, несохранённые поля при grant/revoke,
  пагинация с limit=1, отсутствие лишней навигации и ширины 320/390/768/1440.
  Отчёт: /tmp/stage5-recovery.json; снимок: /tmp/stage5-recovery-grants.png.
  Полный pytest остаётся 215 passed; Ruff/формат/контракт проходят.

## Границы проверки

Для сценария плеера использован реальный двухсекундный H.264/AAC 320×180.
Это не нагрузочное испытание и не проверка максимального 1 GiB/двухчасового Full HD.
Firefox/Safari, power-loss, сетевые файловые системы и публичный HTTPS не проверялись.
Ранее переданные/буферизованные байты и уже начатую раздачу отозвать невозможно;
проверка доступа действует на каждый новый запрос. Tombstone и служебные записи
пока сохраняются; политика их срока хранения остаётся задачей перед публичным запуском.

Контрольная точка M1 проверена в локальном контуре. Главная лента, поиск,
каналы и подписки — следующий этап 6; лайки/комментарии — этап 7.
