# Проверки этапа 3: загрузка и постоянное хранение

Ветка `feature/stage-3-video-upload` создана от `work` на `e5d4552`.
Это результаты локальной облачной среды, не подтверждение GitHub Actions.

## Реализация

- PUT `/api/videos/{id}/content` принимает бинарный поток после создания карточки.
  Сессия, CSRF, владение и допуск проверяются до чтения тела. Content-Length
  необязателен, фактический размер ограничен всегда; известная длина сверяется.
- `upload_attempts` хранит попытку, владельца, резерв, аренду и ID задания.
  Одна короткая транзакция под общей строкой `upload_admission` проверяет и
  резервирует персональную/общую квоту, слоты и место в очереди. Во время
  передачи нет долгой транзакции или занятого сессионного соединения.
- Имена файлов полностью серверные: `uploads/<attempt UUID>/source.part`.
  Запись разбита на части, fsync файла и каталогов предшествует atomic rename
  в `source.mp4`. Нет чтения всего файла в приложении или публичного mount.
- Продление аренды использует время БД; завершение допускается только для
  текущей неистёкшей попытки. `flock` препятствует удалению файла живого писателя.
  Просроченный писатель не может зафиксировать исходник или затереть новую попытку.
- Source pointer, processing и задание Procrastinate фиксируются одной транзакцией
  через то же psycopg-соединение. Ошибка после rename оставляет попытку для
  очистки; потерянный HTTP-ответ после commit не удаляет принятые данные.
- `upload-maintenance` повторяет очистку истёкших/неудачных попыток; резерв и слот
  освобождаются после удаления файла. Ошибка удаления удерживает резерв.
  Очистка защищена от отмены HTTP-задачи вместе с группой задач Starlette.
- Nginx получает MAX_UPLOAD_BYTES и таймауты из тех же env; buffering выключен
  для content. Другие маршруты сохраняют 1 MiB. Volume media не доступен Nginx.
- `/upload` и форма существующей карточки: выбор файла, private по умолчанию,
  метаданные, XHR progress, отмена, проверка статуса и повтор в ту же карточку.
  100% передачи и processing показаны отдельно. Формат ещё не проверяется.

2 MiB. Полный 1 GiB файл и нагрузочная вместимость сервера не измерялись.
В SIGKILL-проверке срок аренды сдвигался временем в тестовой БД, чтобы не ждать
обычные 120 секунд. Синтетический HTTP payload проверяет транспорт, не кодеки.
Браузерная проверка использовала настоящий MP4 размером 73 941 байт.
Firefox/Safari/WebKit не проверены.

## Очередь и границы этапа

Миграция 0004 использует неизменённый SQL-снимок Procrastinate 3.11.0,
SHA-256 `d1f91ba563f92376c631a7d88cb54a5fdc849d5ff104fcc6d157a8a1227f779f`,
с лицензией MIT рядом. Схема выделена в `video_queue`. SQL-функциям закреплён
search_path для работы внутренних триггеров при квалифицированном доступе из public.

Задание `videos.process(video_id, attempt_id)` сохраняется, **worker не запущен**.
По умолчанию после 100 ожидающих/принимаемых видео новые передачи получают 503.
FFprobe, проверка фактического профиля, превью, faststart, повторы обработки и
переход ready — этап 4. Stream/thumbnail, воспроизведение и удаление — этап 5.
Принятые исходники не удаляются уборщиком просроченных передач.

Гарантии относятся к локальному POSIX-хранилищу одного сервера и процессным
сбоям. Аварийное отключение питания, сетевое хранилище, копирование/восстановление
и нагрузочная устойчивость в этом этапе не испытывались.

Команды браузерной, HTTP- и SIGKILL-проверок: [experiments/README.md](../../experiments/README.md).
