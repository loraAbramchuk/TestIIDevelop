# Подтверждение email и восстановление пароля

Регистрация открыта. Новый пользователь получает сессию и письмо; до
подтверждения адреса он может читать доступные видео и входить в аккаунт,
но не может менять контент, подписываться или выполнять действия модерации.
Для локальной проверки внешний SMTP не нужен: `bash scripts/start.sh` поднимает
Mailpit. Подтверждение и восстановление остаются обязательными сценариями;
письма доступны в http://localhost:8025 и не уходят на настоящие адреса.
Провайдер для публичной отправки пока не выбран.

## Локальная почта из коробки

`MAIL_BACKEND=auto` выбирает заданный `SMTP_HOST`, а при его отсутствии —
Mailpit для loopback HTTP с non-Secure cookies. Значения `smtp` и `mailpit`
выбирают режим явно. Непубличный ящик слушает loopback: HTTP 8025, SMTP 1025;
порты меняются через `MAILPIT_HTTP_PORT`/`MAILPIT_SMTP_PORT`. В Docker app/worker
обращаются к внутреннему сервису `mailpit:1025`; Python на хосте — к 127.0.0.1:1025.
`MAILPIT_PORT`/`MAILPIT_UI_URL` задают адреса для запуска Python вне Compose.

На страницах есть ссылка на тестовый ящик. После регистрации откройте письмо,
перейдите по ссылке и подтвердите адрес отдельной кнопкой. Существующий worker
отправляет письмо через ту же очередь. Автоматического подтверждения новых
публичных регистраций нет. Письма в Mailpit исчезают при пересоздании его
контейнера: при необходимости запросите новое письмо обычной кнопкой.

Production overlay принудительно выбирает `smtp` для всех прикладных сервисов,
а Mailpit не запускается по умолчанию. Local fallback запрещён для публичного
origin или Secure cookies. Ящик содержит ссылки доступа и предназначен только
для локальной разработки, без внешнего port forwarding.

## Настройка внешнего SMTP

Для нового `.env` `scripts/init_env.py` создаёт случайный `AUTH_MAIL_SECRET`.
Локальный launcher сам добавляет отсутствующий ключ, сохраняя старые секреты.
Для существующей SMTP-установки добавьте отсутствующий ключ отдельной командой:

```bash
python3 scripts/init_env.py --prepare-mail
```

Она не выводит ключ и не заменяет существующие пароли/настройки; повторный
запуск сохраняет имеющийся ключ. `.env` записывается с правами 0600.
Затем оператор заполняет в этом файле параметры выбранного SMTP-провайдера:

```dotenv
AUTH_REQUIRE_VERIFIED_EMAIL=true
MAIL_BACKEND=smtp
PUBLIC_BASE_URL=https://video.example.com
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_SECURITY=starttls
SMTP_FROM=noreply@example.com
SMTP_USERNAME=your-smtp-user
SMTP_PASSWORD=your-smtp-password
```

Используйте настоящие значения своего провайдера и домена. Для SMTPS/465
установите `SMTP_SECURITY=tls`. Сертификат и имя сервера проверяются через
системное доверенное хранилище CA. `plain` разрешён только для SMTP на loopback
в изолированных тестах. Не включайте SMTP debug logging и не передавайте пароль
аргументом командной строки. Настройку SPF/DKIM и лимиты отправки задаёт провайдер.

После настройки используется обычный `bash scripts/start.sh`. Сначала применится
миграция `0012`, затем запустятся приложение и worker. Отправка писем не работает
без worker. Его остановка не закрывает просмотр ранее готовых видео.

`PUBLIC_BASE_URL` — явно заданный origin без credentials, query, fragment или
префикса пути. Входящий заголовок Host не используется для построения ссылок.
При Secure cookies и настроенной почте требуется HTTPS-origin.

В явно выбранном SMTP-режиме без host/from/signing secret API возвращает 503
без создания аккаунта. Launcher обнаруживает этот случай до сборки/остановки
сервисов и указывает нужные настройки. Для обычного локального запуска Mailpit
позволяет пройти регистрацию и первый вход без ручной настройки провайдера.
`diagnostics.mail_delivery=configured` означает наличие настроек, а не проверку
доставки провайдером; HTTP readiness по-прежнему описывает возможность просмотра.

## Сценарии и API

Для POST нужны сессионная cookie и актуальный `X-CSRF-Token` из `/api/auth/csrf`.

| Действие | Экран | API |
| --- | --- | --- |
| Регистрация | `/register` | `POST /api/auth/register` |
| Повтор письма подтверждения | Панель неподтверждённого аккаунта | `POST /api/auth/email/request` |
| Подтверждение адреса | `/verify-email#token=...` | `POST /api/auth/email/verify` |
| Запрос восстановления | `/forgot-password` | `POST /api/auth/password/request` |
| Новый пароль | `/reset-password#token=...` | `POST /api/auth/password/reset` |

Ссылки содержат token в fragment: он не отправляется HTTP-серверу и удаляется
из истории страницы после чтения JavaScript. Открытие ссылки не меняет состояние;
подтверждение выполняется только отдельным POST по кнопке. Письмо, открытое
почтовым сканером, не расходует ссылку.

Срок действия: подтверждение — 60 минут, восстановление — 30 минут. Ссылка
одноразовая; новый запрос того же действия делает предыдущую ссылку недействительной.
Письмо может прийти повторно после сбоя SMTP/worker: повтор содержит ту же
одноразовую ссылку и не позволяет выполнить действие дважды.

В БД хранится SHA-256 токена; подпись восстанавливается из случайного идентификатора,
назначения и серверного HMAC-ключа. В PostgreSQL-очередь передаётся только ID записи,
без адреса, пароля или полной ссылки. Письма используют существующую Procrastinate
очередь в отдельном `auth-mail` потоке того же worker, независимо от видео.
Ошибки SMTP очищаются от адресов/диагностики; повторы ограничены тремя попытками.
Зависшие после аварии задания восстанавливает штатный upload-maintenance.
Истёкшие записи ссылок очищаются порциями после суток с момента истечения.

Ответ запроса восстановления одинаков для существующего и неизвестного адреса.
Лимиты запросов: 15/IP/час и 5/адрес/час; попытки использования ссылок —
30/IP/час. Пароль сохраняет прежнюю политику 12–128 символов и Argon2id.
После сброса завершаются все сессии аккаунта, включая вход, конкурирующий
со сменой пароля. Автоматического входа по reset-link нет.

При повреждённом/потерянном ответе браузер не повторяет POST автоматически:
сохраняет поля и предлагает проверить аккаунт или войти с новым паролем.
Токены и пароли не сохраняются в localStorage или URL query.

## Обновление и восстановление

Миграция не объявляет старые адреса подтверждёнными: владельцы существующих
аккаунтов подтверждают email после подключения SMTP. Просмотр доступного контента
и вход сохраняются. Администратор, созданный оператором через CLI, считается
доверенной учётной записью; публичная регистрация не может задать роль или признак
подтверждения. Понижение `AUTH_REQUIRE_VERIFIED_EMAIL` используется лишь в старых
независимых тестах предметных модулей; профиль выпуска требует `true`.

Храните signing secret вместе с защищённой конфигурацией и резервными копиями.
Его ручная смена делает ранее выданные ссылки недействительными: потребуется
запросить новые письма. Существующий ключ не перезаписывается установщиком.

При восстановлении старого снимка время откатывается и для состояний сессий/
ссылок. До открытия сервиса оператор должен завершить восстановленные сессии
и пометить старые ссылки использованными, затем проверить вход и почту заново.
Например, после миграции восстановленного контура, при закрытом внешнем трафике:

```bash
docker compose exec -T app python - <<'PY'
from datetime import UTC, datetime
from sqlalchemy import delete, update
from app.config import Settings
from app.db import make_engine, make_session_factory
from app.models import AuthSession, AuthMailToken
engine = make_engine(Settings())
with make_session_factory(engine)() as db:
    db.execute(delete(AuthSession))
    db.execute(update(AuthMailToken).values(used_at=datetime.now(UTC)))
    db.commit()
engine.dispose()
PY
```

Это операторская процедура восстановления, не действие при обычном перезапуске.
Возврат старого backup может также восстановить прежние пароли, удалённые видео
или разрешения: до публичного открытия нужно учесть изменения после снимка.
Автоматическое восстановление SMTP-настроек не заменяет такую приёмку.
