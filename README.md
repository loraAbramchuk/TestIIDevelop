# Видеоплатформа

Каркас Python 3.12 + FastAPI + PostgreSQL 17. Nginx принимает HTTP-запросы,
Alembic управляет схемой базы, Jinja2 отображает простую главную страницу.

Реализованы инфраструктура, пользователи с ролями `user`, `moderator`, `admin`,
регистрация, вход и выход с серверными сессиями, Swagger и проверки готовности.
Реализованы карточки видео, владение, приватные разрешения и экран «Мои видео».
Передача файлов, обработка и воспроизведение пока не реализованы.

Требования: [спецификация](docs/requirements.md), [сценарии приёмки](docs/acceptance.md).
Архитектура: [компоненты, модули, данные и жизненный цикл видео](docs/architecture.md).
Разработка: [пошаговый план по модулям и критериям готовности](docs/development-plan.md).
Этап 1: [контракт видео](docs/api/video-contract.md), [профиль и лимиты](docs/video-policy.md),
[решение по очереди](docs/decisions/0001-postgresql-queue.md).
Этап 2: [модели, права и проверки](docs/verification/stage-2.md).

## Локальный запуск

Нужны Docker Engine с Compose v2 (`--wait`) и Python 3.12 для разработки
(для генерации конфигурации достаточно Python 3 из стандартного пакета Ubuntu).
Из корня репозитория:

```bash
bash scripts/start.sh
```

Скрипт создаёт `.env` с уникальным случайным паролем БД и правами `0600`, если
файл ещё отсутствует. Затем собирает образ, запускает PostgreSQL, применяет
миграции отдельным контейнером и ожидает готовности приложения и Nginx.
Существующая конфигурация сохраняется. `.env` не коммитится.

На своей машине откройте порт 8080: главная `/`, Swagger `/docs`, схема
`/openapi.json`. Порт привязан только к loopback. Изменить порт можно через
`HTTP_PORT` в `.env`. БД и Python-приложение не публикуют порты наружу.

Это запуск каркаса с установленным Docker. Установщик зависимостей для чистой
Ubuntu, публичный HTTPS и обработчик видео будут добавлены в следующих этапах.

## Разработка без пересборки образа

Нужны Python 3.12 и [uv](https://docs.astral.sh/uv/). Из корня репозитория:

```bash
python3 scripts/init_env.py
uv sync --locked
docker compose -f compose.yaml -f compose.dev.yaml up -d --wait db
uv run --locked alembic upgrade head
uv run --locked uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

`compose.dev.yaml` открывает PostgreSQL только на `127.0.0.1:5432`.
Приложение читает `.env`, `DB_HOST` по умолчанию — `localhost`. Локальные файлы
хранятся в игнорируемом `.local/media`. Каталог видео не подключён как публичная
статика. Контейнерный вариант использует отдельный постоянный volume `media`.

В управляемой облачной среде каталог кэша uv может быть недоступен для записи:
используйте `UV_CACHE_DIR=/tmp/video-uv-cache` перед командами uv. Для сборки
через доверенный прокси `start.sh` автоматически использует `compose.cloud.yaml`,
если задан `CODEX_PROXY_CERT`. Можно также задать `BUILD_CA_BUNDLE` — путь к
доверенному объединённому CA bundle на машине сборки. Сертификат передаётся как
BuildKit secret; проверка TLS остаётся включённой.

## Проверки

```bash
uv run --locked ruff check app migrations tests scripts experiments
uv run --locked ruff format --check app migrations tests scripts experiments
uv run --locked python scripts/export_video_contract.py --check
uv run --locked pytest -m 'not integration'
# После запуска dev-БД и alembic upgrade head:
RUN_DB_TESTS=1 uv run --locked pytest
uv run --locked alembic check
```

Интеграционные тесты используют настоящий PostgreSQL и транзакции с откатом.
Запускайте их на БД разработки или отдельной тестовой БД, не в production.
Без `RUN_DB_TESTS=1` проверки PostgreSQL явно пропускаются.

`/health/live` проверяет HTTP-процесс. `/health/ready` возвращает 200, если
доступны прикладная схема БД и чтение служебного маркера в хранилище; иначе — 503.
Маркер `.storage-readiness` создаётся один раз при инициализации. Готовность
просмотра не зависит от записи в media и состояния будущего worker.
`/health/diagnostics` дополнительно проверяет реальную запись временного файла
и запас места, возвращая status=degraded при проблеме приёма файлов. HTTP 200
у diagnostics означает получение диагностики; состояние нужно читать из JSON.
Обработчик и загрузка видео пока обозначены как not_configured/not_implemented,
поэтому эти ответы не заявляют готовность видеоподсистемы. Главная — пустое
состояние, не проверка содержимого видеокаталога.

## Миграции и зависимости

```bash
uv run --locked alembic revision --autogenerate -m 'describe change'
uv run --locked alembic upgrade head
```

Проверяйте сгенерированные миграции перед применением. Приложение не вызывает
`create_all` при запуске. Пользователи и пароли по умолчанию не создаются.

`uv.lock` фиксирует все зависимости, `requirements.txt` — сгенерированный
runtime-экспорт с хешами для Docker. После изменения зависимостей:

```bash
uv lock
uv export --frozen --no-dev --no-emit-project --format requirements-txt --output-file requirements.txt
```

Procrastinate 3.11.0 пока установлен только в группе `experiments`, без
production-миграций очереди. Примеры файлов, испытание очереди с SIGKILL и
браузерная проверка описаны в [experiments/README.md](experiments/README.md).
Поддержка stage-1 профиля в рабочей загрузке появится на последующих этапах.
Контракт отмечает x-implemented по действующему router: метаданные и grants
реализованы, операции с файлами остаются проектными.

## Авторизация

Экраны `/register` и `/login` используют тот же API, что и Swagger. После
регистрации пользователь сразу входит; в шапке появляются имя и кнопка выхода.
Email нормализуется в нижний регистр, пароль — от 12 до 128 символов.
Пароли хешируются Argon2id. Публичная регистрация принимает только email,
пароль и имя и всегда создаёт роль `user`; попытка передать роль отклоняется.

| Метод | Адрес | Назначение |
| --- | --- | --- |
| GET | `/api/auth/csrf` | Открыть анонимную сессию при необходимости, получить CSRF-токен |
| POST | `/api/auth/register` | Создать аккаунт и новую сессию |
| POST | `/api/auth/login` | Проверить пароль и создать новую сессию |
| GET | `/api/auth/me` | Данные текущего пользователя; 401 без действующей сессии |
| POST | `/api/auth/logout` | Удалить сессию на сервере и cookie |

Для POST передавайте `X-CSRF-Token` из GET `/api/auth/csrf` и cookie той же
сессии. Это относится и к входу/регистрации. После входа CSRF-токен меняется;
новый приходит в ответе или получается повторным GET. В Swagger сначала
выполните GET, затем вставьте токен в заголовок POST; браузер передаст cookie.

Сессия — случайный непрозрачный токен в HttpOnly/SameSite=Lax cookie. В БД
сохраняется только SHA-256 токена. Анонимная сессия действует 30 минут,
авторизованная — 14 дней с момента входа (настройка `SESSION_LIFETIME_HOURS`),
без автоматического продления. Старый токен при входе отзывается, при выходе
удаляется. Сессии переживают перезапуск приложения. Истёкшие сессии и старые
счётчики автоматически очищаются при создании новых анонимных сессий.

Для HTTPS установите `AUTH_COOKIE_SECURE=true`: cookie получит флаг Secure и
имя `__Host-video_session` без Domain, с Path=/. Для локального HTTP оставьте
`false`. На публичном сервере настройте HTTPS до открытия регистрации.
Cookie не хранится в localStorage; приватные ответы не кэшируются.

Ограничения хранятся в PostgreSQL и действуют для всех HTTP-процессов:
регистрация — 5 попыток/IP/час, вход — 30/IP и 10/email за 15 минут,
создание анонимной сессии — 60/IP/минуту. Ответ 429 содержит `Retry-After`.
Успешный вход не сбрасывает лимиты. Приложение самостоятельно не читает
присланный клиентом `X-Forwarded-For`. В Compose доверие proxy headers включено
только для внутреннего приложения за Nginx; Nginx перезаписывает эти заголовки.
Не открывайте порт приложения напрямую при такой конфигурации доверия.

Первого администратора создают интерактивной командой:

```bash
docker compose exec app python -m app.cli create-admin --email admin@example.com --name Administrator
# Или при локальном запуске Python:
uv run --locked python -m app.cli create-admin --email admin@example.com --name Administrator
```

Пароль вводится дважды без отображения и не передаётся в аргументах команды.
Существующий аккаунт не изменяется. Для будущих закрытых API используйте
`CurrentUser`, для проверки роли — `Depends(require_roles("moderator", "admin"))`.
Роль читается из БД при каждом запросе. Интерфейс назначения ролей,
восстановление пароля и подтверждение email ещё не реализованы.

## Управление своими видео — этап 2

После входа откройте «Мои видео» (`/studio`): можно создать карточку, поменять
название, описание и видимость, увидеть состояние, выдать и отозвать разрешение.
Для приглашения нужен ID существующего пользователя; свой ID он видит в `/studio`.
Письма и уведомления не отправляются. Карточка начинается в uploading/private;
присвоить ready или изменить владельца через API нельзя.

| Метод | Endpoint | Доступ |
| --- | --- | --- |
| POST | `/api/videos` | Создать свои метаданные |
| GET | `/api/studio/videos` | Свои карточки, пагинация |
| GET | `/api/videos/{id}/status` | Только владелец, включая неготовые и скрытые |
| PATCH | `/api/videos/{id}` | Только владелец, title/description/visibility |
| GET | `/api/videos/{id}` | Готовое, видимое, неудалённое видео: public/владелец/grant |
| GET | `/api/videos/{id}/grants` | Только владелец, пагинация |
| PUT/DELETE | `/api/videos/{id}/grants/{user_id}` | Только владелец, идемпотентная выдача/отзыв |

Сессия и CSRF обязательны для изменений. Роли moderator/admin не дают права
управлять чужими карточками или смотреть приватные данные без разрешения.
Новые запросы после отзыва grants/смены приватности учитывают актуальные права.
Лимиты на пользователя: `VIDEO_CREATE_LIMIT_PER_HOUR=30`,
`VIDEO_WRITE_LIMIT_PER_MINUTE=120`; 429 содержит Retry-After.

Тесты готового состояния используют контролируемые записи БД. Пользовательский
API пока не умеет загружать файл или делать видео готовым. Поля stream_url и
thumbnail_url в VideoView резервируют будущие пути, а не обещают раздачу файла.
Удаление видео с очисткой появится вместе с файловой подсистемой; сейчас endpoint
DELETE video не регистрируется.

Миграция 0003 добавляет videos/video_grants без изменения учётных записей.
Её downgrade удаляет эти новые таблицы с данными; на рабочей БД его нельзя
использовать как безопасный автоматический откат без резервной копии.

## Управление сервисами и данными

```bash
docker compose ps
docker compose logs --tail=100 app migrate web
docker compose stop
bash scripts/start.sh
```

Повторный запуск применяет только новые миграции. База и хранилище живут в
именованных volumes и сохраняются при пересоздании контейнеров.
Не используйте `docker compose down -v` для обычной остановки: это удалит данные.
Не меняйте пароль в `.env` уже созданной БД без отдельной смены пароля в PostgreSQL.
Резервное копирование и восстановление ещё не реализованы.
