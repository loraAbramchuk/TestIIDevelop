# Видеоплатформа

Видеоплатформа на Python 3.12 + FastAPI + PostgreSQL 17. Nginx принимает
HTTP-запросы, Alembic управляет схемой базы, Jinja2 отображает простые HTML-экраны.

Реализованы инфраструктура, пользователи с ролями `user`, `moderator`, `admin`,
регистрация, вход и выход с серверными сессиями, Swagger и проверки готовности.
Реализованы карточки видео, владение, приватные разрешения и экран «Мои видео».
Добавлены потоковая загрузка, квоты, постоянное хранение и очередь обработки.
Worker проверяет профиль, подготавливает MP4/превью и переводит видео в ready.
Работают защищённая раздача через Nginx, плеер с перемоткой и удаление с фоновой очисткой.
Добавлены публичная лента, поиск по названию, каналы и подписки.
На странице просмотра работают лайки, комментарии, их счётчики и удаление своего комментария.
Работают публичные плейлисты с управлением составом и порядком видео.
Добавлены жалобы, очередь модерации, скрытие/восстановление и журнал действий.
Администратор управляет ролями через поиск пользователей и отдельную историю изменений.

## Интерфейс

Лёгкий интерфейс в стиле видеосервиса: боковое меню, поиск, сетка превью,
страница плеера с другими видео, оформление каналов и меню аккаунта.
Адаптирован для телефона и клавиатуры. Фронт работает на существующих
Jinja2-шаблонах и локальных CSS/JavaScript, отдельная сборка не требуется.
[Описание и проверки](docs/verification/frontend.md).

## Локальный запуск

Нужны Docker Engine с Compose >= 2.24.4 и Python 3.12 для разработки
(для генерации конфигурации достаточно Python 3 из стандартного пакета Ubuntu).
Из корня репозитория:

```bash
bash scripts/start.sh
```

Скрипт создаёт `.env` с уникальным случайным паролем БД и правами `0600`, если
файл ещё отсутствует. Затем собирает образ, запускает PostgreSQL, применяет
миграции отдельным контейнером и ожидает готовности приложения, worker и Nginx.
Существующая конфигурация сохраняется. `.env` не коммитится.

На своей машине откройте порт 8080: главная `/`, Swagger `/docs`, схема
`/openapi.json`. Порт привязан только к loopback. Изменить порт можно через
`HTTP_PORT` в `.env`. БД и Python-приложение не публикуют порты наружу.
Swagger UI 5.35.0, стили и favicon включены в приложение: `/docs` не требует
доступа к CDN и не отправляет схему внешнему валидатору.

Установщик для Ubuntu 24.04, HTTPS, внешние зашифрованные копии и восстановление:
[инструкция оператора](docs/deployment.md). Публичный домен и сервер настраиваются
по этой инструкции; границы выполненных проверок указаны в отчёте этапа 11.

## Разработка без пересборки образа

Нужны Python 3.12 и [uv](https://docs.astral.sh/uv/). Из корня репозитория:

```bash
python3 scripts/init_env.py
uv sync --locked
docker compose -f compose.yaml -f compose.dev.yaml up -d --wait db
uv run --locked alembic upgrade head
uv run --locked uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

`compose.dev.yaml` открывает PostgreSQL только на `127.0.0.1:5432`.
Приложение читает `.env`, `DB_HOST` по умолчанию — `localhost`. Локальные файлы
хранятся в игнорируемом `.local/media`. Каталог видео не подключён как публичная
статика. Контейнерный вариант использует отдельный постоянный volume `media`.

В управляемой облачной среде каталог кэша uv может быть недоступен для записи:
используйте `UV_CACHE_DIR=/tmp/video-uv-cache` перед командами uv. Для сборки
через доверенный прокси `start.sh` автоматически использует `compose.cloud.yaml`,
если задан `CODEX_PROXY_CERT`. Можно также задать `BUILD_CA_BUNDLE` — путь к
доверенному объединённому CA bundle на машине сборки. Сертификат передаётся как
BuildKit secret; проверка TLS остаётся включённой.

## Проверки

```bash
uv run --locked ruff check app migrations tests scripts experiments
uv run --locked ruff format --check app migrations tests scripts experiments
uv run --locked python scripts/export_video_contract.py --check
uv run --locked pytest -m 'not integration'
# После запуска dev-БД и alembic upgrade head:
RUN_DB_TESTS=1 uv run --locked pytest
uv run --locked alembic check
```

Интеграционные тесты используют настоящий PostgreSQL. Проверки потоковой загрузки
создают данные с commit на независимых соединениях и удаляют свои записи после проверки.
Запускайте их на БД разработки или отдельной тестовой БД, не в production.
Без `RUN_DB_TESTS=1` проверки PostgreSQL явно пропускаются.

`/health/live` проверяет HTTP-процесс. `/health/ready` возвращает 200, если
доступны прикладная схема БД и чтение служебного маркера в хранилище; иначе — 503.
Маркер `.storage-readiness` создаётся один раз при инициализации. Готовность
просмотра не зависит от записи в media и состояния worker.
`/health/diagnostics` дополнительно проверяет реальную запись временного файла
и запас места, возвращая status=degraded при проблеме приёма файлов. HTTP 200
у diagnostics означает получение диагностики; состояние нужно читать из JSON.
Диагностика проверяет также таблицу очереди и лимит ожидающих заданий;
video_uploads=available/unavailable описывает общий приём файлов, но не заменяет
проверку персональной квоты в запросе. processing=ok/error отражает свежесть heartbeat worker. Его остановка делает
диагностику degraded, но не блокирует HTTP readiness и приём до лимита очереди.
Главная отображает публичные готовые видео; при отсутствии видео — пустое состояние.

## Миграции и зависимости

```bash
uv run --locked alembic revision --autogenerate -m 'describe change'
uv run --locked alembic upgrade head
```

Проверяйте сгенерированные миграции перед применением. Приложение не вызывает
`create_all` при запуске. Пользователи и пароли по умолчанию не создаются.

`uv.lock` фиксирует все зависимости, `requirements.txt` — сгенерированный
runtime-экспорт с хешами для Docker. После изменения зависимостей:

```bash
uv lock
uv export --frozen --no-dev --no-emit-project --format requirements-txt --output-file requirements.txt
```

Procrastinate 3.11.0 — runtime-зависимость. Миграция 0004 создаёт его схему
в namespace video_queue из неизменяемого SQL-снимка с проверкой SHA-256;
0005 добавляет попытки загрузки, резерв квот и ссылку видео на исходник.
Лицензия MIT находится рядом со снимком в migrations/sql. Изменения версии
очереди требуют отдельной миграции, а не замены старого SQL-файла.
Примеры файлов и проверки сбоев: [experiments/README.md](experiments/README.md).
Контракт отмечает x-implemented по действующим routers: метаданные, grants,
PUT content, stream/thumbnail, удаление, каталог, каналы и подписки реализованы.

## Авторизация

Экраны `/register` и `/login` используют тот же API, что и Swagger. После
регистрации пользователь получает сессию; для действий с контентом требуется
подтверждение адреса. Для повторного письма доступна панель аккаунта, для сброса
пароля — ссылка «Забыли пароль?» на экране входа. В шапке появляются имя и выход.
Email нормализуется в нижний регистр, пароль — от 12 до 128 символов.
Имена, названия и описания отклоняют NUL и некорректный Unicode с ответом 422;
кириллица и emoji поддерживаются. При временном сбое форма показывает понятное
сообщение и сохраняет ввод для повторной попытки.
Некорректный Unicode в пароле также отклоняется с 422 до хеширования.
Пароль не обрезается и не нормализуется: пробелы и корректный Unicode сохраняются.
Пароли хешируются Argon2id. Публичная регистрация принимает только email,
пароль и имя и всегда создаёт роль `user`; попытка передать роль отклоняется.

| Метод | Адрес | Назначение |
| --- | --- | --- |
| GET | `/api/auth/csrf` | Открыть анонимную сессию при необходимости, получить CSRF-токен |
| POST | `/api/auth/register` | Создать аккаунт и новую сессию |
| POST | `/api/auth/login` | Проверить пароль и создать новую сессию |
| GET | `/api/auth/me` | Данные текущего пользователя; 401 без действующей сессии |
| POST | `/api/auth/logout` | Удалить сессию на сервере и cookie |
| POST | `/api/auth/email/request` | Повторить письмо подтверждения |
| POST | `/api/auth/email/verify` | Подтвердить адрес одноразовой ссылкой |
| POST | `/api/auth/password/request` | Запросить восстановление, одинаковый ответ для известного и неизвестного адреса |
| POST | `/api/auth/password/reset` | Сменить пароль по ссылке и отозвать все прежние сессии |

Для POST передавайте `X-CSRF-Token` из GET `/api/auth/csrf` и cookie той же
сессии. Это относится и к входу/регистрации. После входа CSRF-токен меняется;
новый приходит в ответе или получается повторным GET. В Swagger сначала
выполните GET, затем вставьте токен в заголовок POST; браузер передаст cookie.

Сессия — случайный непрозрачный токен в HttpOnly/SameSite=Lax cookie. В БД
сохраняется только SHA-256 токена. Анонимная сессия действует 30 минут,
авторизованная — 14 дней с момента входа (настройка `SESSION_LIFETIME_HOURS`),
без автоматического продления. Старый токен при входе отзывается, при выходе
удаляется. Сессии переживают перезапуск приложения. Истёкшие сессии и старые
счётчики автоматически очищаются при создании новых анонимных сессий.

Для HTTPS установите `AUTH_COOKIE_SECURE=true`: cookie получит флаг Secure и
имя `__Host-video_session` без Domain, с Path=/. Для локального HTTP оставьте
`false`. На публичном сервере настройте HTTPS до открытия регистрации.
Cookie не хранится в localStorage; приватные ответы не кэшируются.

Ограничения хранятся в PostgreSQL и действуют для всех HTTP-процессов:
регистрация — 5 попыток/IP/час, вход — 30/IP и 10/email за 15 минут,
создание анонимной сессии — 60/IP/минуту. Ответ 429 содержит `Retry-After`.
Успешный вход не сбрасывает лимиты. Приложение самостоятельно не читает
присланный клиентом `X-Forwarded-For`. В Compose доверие proxy headers включено
только для внутреннего приложения за Nginx; Nginx перезаписывает эти заголовки.
Не открывайте порт приложения напрямую при такой конфигурации доверия.

Первого администратора создают интерактивной командой:

```bash
docker compose exec app python -m app.cli create-admin --email admin@example.com --name Administrator
# Или при локальном запуске Python:
uv run --locked python -m app.cli create-admin --email admin@example.com --name Administrator
```

Пароль вводится дважды без отображения и не передаётся в аргументах команды.
Существующий аккаунт не изменяется. Для API, требующих входа, используйте
`CurrentUser`, для действий с контентом — `VerifiedUser`, для проверки роли —
`Depends(require_roles("moderator", "admin"))`.
Роль читается из БД при каждом запросе. Назначение ролей доступно администратору
на `/admin/users`. Подтверждение email и восстановление пароля описаны в
[инструкции по SMTP](docs/email.md).

После входа или регистрации по ссылке из канала пользователь возвращается к
этому каналу. Параметр `next` сохраняется между экранами входа/регистрации и
принимает только адрес внутри сайта. Защищённые страницы также сохраняют свой
адрес при перенаправлении на вход; без `next` открывается главная.

## Управление своими видео — этап 2

После входа откройте «Мои видео» (`/studio`): можно создать карточку, поменять
название, описание и видимость, увидеть состояние, выдать и отозвать разрешение.
Для приглашения нужен ID существующего пользователя; свой ID он видит в `/studio`.
Письма и уведомления не отправляются. Карточка начинается в uploading/private;
присвоить ready или изменить владельца через API нельзя.

| Метод | Endpoint | Доступ |
| --- | --- | --- |
| POST | `/api/videos` | Создать свои метаданные |
| GET | `/api/studio/videos` | Свои карточки, пагинация |
| GET | `/api/videos/{id}/status` | Только владелец, включая неготовые и скрытые |
| PATCH | `/api/videos/{id}` | Только владелец, title/description/visibility |
| GET | `/api/videos/{id}` | Готовое, видимое, неудалённое видео: public/владелец/grant |
| GET | `/api/videos/{id}/grants` | Только владелец, пагинация |
| PUT/DELETE | `/api/videos/{id}/grants/{user_id}` | Только владелец, идемпотентная выдача/отзыв |

Сессия и CSRF обязательны для изменений. Роли moderator/admin не дают права
управлять чужими карточками или смотреть приватные данные без разрешения.
Новые запросы после отзыва grants/смены приватности учитывают актуальные права.
Лимиты на пользователя: `VIDEO_CREATE_LIMIT_PER_HOUR=30`,
`VIDEO_WRITE_LIMIT_PER_MINUTE=120`; 429 содержит Retry-After.

Матрица доступа этапа 2 использует контролируемые записи БД; обработка этапа 4
проверяется на настоящих media-файлах. Пользовательский
API принимает файл; worker переводит подготовленный результат в ready.
stream_url и thumbnail_url ведут на защищённые маршруты. На `/watch/{id}`
работает плеер. DELETE video немедленно закрывает доступ и записывает очистку;
файлы и занятая квота освобождаются в фоне.

Миграция 0003 добавляет videos/video_grants без изменения учётных записей.
Её downgrade удаляет эти новые таблицы с данными; на рабочей БД его нельзя
использовать как безопасный автоматический откат без резервной копии.

## Каталог, каналы и подписки — этап 6

Главная `/` показывает публичные готовые видео с превью и автором. Поиск
`/search?q=...` ищет часть названия без учёта регистра; `%`, `_` и другие
спецсимволы считаются обычным текстом. Выдача ограничена страницами.
На `/channels/{id}` посетитель видит доступные ему готовые видео автора.
Приватное видео появляется только у владельца и пользователей с разрешением.
Скрытые, удалённые и неготовые видео в каталоге не отображаются.

«Мой канал» (`/my-channel`) открывает свой канал: владелец меняет название и
описание. Можно подписываться на другие каналы и открывать свой список
`/subscriptions`. Подписка не даёт доступа к приватным видео; разрешения
по-прежнему выдаются отдельно владельцем ролика. Самоподписка запрещена.

API: `GET /api/videos`, `GET /api/channels/me`,
`GET/PATCH /api/channels/{id}`, `GET /api/channels/{id}/videos`,
`PUT/DELETE /api/channels/{id}/subscription`, `GET /api/subscriptions`.
Подробности пагинации и схем — в [контракте](docs/api/video-contract.md).
Изменения требуют сессии и CSRF. Лимит записи каналов —
`VIDEO_WRITE_LIMIT_PER_MINUTE` на пользователя, отдельно от записи видео.

Миграция 0007 создаёт канал каждому существующему пользователю. Регистрация и
CLI создания администратора сохраняют аккаунт и канал одной транзакцией.
Downgrade удаляет профили каналов и подписки, поэтому не является безопасным
откатом на рабочей БД. Плейлисты добавлены на этапе 8.

## Лайки и комментарии — этап 7

На `/watch/{id}` гость видит лайки и комментарии доступного видео. После входа
можно поставить/снять лайк, написать текстовый комментарий до 2000 символов и
удалить свой комментарий. Новые комментарии идут первыми; «Ещё комментарии»
загружает следующую страницу. HTML отображается обычным текстом.

Все чтения, счётчики и изменения используют ту же политику просмотра, что плеер.
Роли moderator/admin не открывают закрытый ролик и не позволяют удалять чужой
комментарий. После отзыва доступа новые запросы возвращают 404; интерфейс очищает
обсуждение при получении отказа. Уже полученные данные отозвать невозможно.

API: `GET/PUT/DELETE /api/videos/{id}/likes`,
`GET/POST /api/videos/{id}/comments`, `DELETE /api/videos/{id}/comments/{comment_id}`.
Изменения требуют сессии и CSRF. Повтор PUT/DELETE лайка не создаёт дублей.
Лимиты на пользователя: `INTERACTION_WRITE_LIMIT_PER_MINUTE=120` для всех
изменений и дополнительно `COMMENT_CREATE_LIMIT_PER_MINUTE=10` для отправки
комментариев; 429 содержит Retry-After. Лимиты работают через PostgreSQL.

Ошибка запроса сохраняет черновик. Отправка комментария автоматически не
повторяется: при потере ответа сначала обновите обсуждение, чтобы не создать
дубликат. Миграция 0008 добавляет likes/comments, сохраняя существующие данные.
Её downgrade удаляет все лайки и комментарии; на рабочей БД нужен резервный снимок.

## Плейлисты — этап 8

После входа откройте «Плейлисты» (`/my-playlists`): создайте список, задайте
название и добавьте видео по ссылке со страницы просмотра этого сайта.
На `/playlists/{id}` доступны переименование, удаление, добавление/удаление
элементов и кнопки «Выше»/«Ниже». Плейлисты также отображаются на канале автора.
Удаление плейлиста или элемента не удаляет видео и не меняет его разрешения.

Все плейлисты публичные, но название/превью недоступного видео и его присутствие
в счётчике не раскрываются посетителю. Владелец плейлиста не получает доступ
к чужому приватному видео автоматически. Скрытие, удаление и отзыв разрешения
учитываются при каждом новом запросе. Редактировать плейлист может только владелец.

Добавление/удаление элемента идемпотентно. Состав и порядок меняются одной
транзакцией с блокировкой плейлиста. При изменении порядка между страницами
API отвечает 409: нажмите «Обновить плейлист». Подписанный курсор не раскрывает
номера скрытых позиций. Ошибки записи сохраняют введённое название и ссылку.
При обновлении чистое поле названия синхронизируется с сервером, настоящий
черновик сохраняется. Если запись прошла, а обновление списка не удалось,
интерфейс подтверждает запись и предлагает перечитать список без повторной отправки.
После удаления плейлиста в другой вкладке управление отключается и появляется
ссылка к своим плейлистам.

«Убрать недоступные видео» освобождает занятые ими места после подтверждения
владельца. Действие меняет только состав списка, не удаляет видео и не раскрывает
их названия, идентификаторы или количество. При восстановлении доступа видео
нужно добавить снова; автоматической очистки нет.

Лимиты: `PLAYLIST_CREATE_LIMIT_PER_HOUR=30`, `PLAYLIST_WRITE_LIMIT_PER_MINUTE=120`
на пользователя и `PLAYLIST_MAX_ITEMS=1000` элементов на список. При заполнении
плейлиста добавление нового элемента даёт 409, повтор существующего не создаёт
дубль. Все изменения требуют сессии и CSRF. API и схемы описаны в
[контракте](docs/api/video-contract.md). Миграция 0009 добавляет только playlists
и playlist_items. Downgrade удаляет их данные; нужен резервный снимок для отката.

## Загрузка и хранение — этап 3

Откройте `/upload` после входа: выберите файл, название, описание и видимость.
Для существующей карточки файл добавляется на `/studio/videos/{id}`.
Прогресс показывает отправку байтов; **202 означает сохранение исходника и
задания в БД**. Worker подготавливает файлы и переводит видео в ready или failed;
кнопка «Проверить статус» обновляет состояние. Плеер и раздача — этап 5.

API: сначала POST `/api/videos`, затем PUT `/api/videos/{id}/content` с телом
`application/octet-stream`, сессионной cookie и X-CSRF-Token. Content-Length
необязателен; при его наличии проверяется совпадение с фактическими байтами.
Размер, квоты, слоты, очередь и таймауты берутся из `.env.example`.
Nginx подставляет тот же размер и таймауты из env только для content, без
буферизации запроса. Остальные маршруты сохраняют лимит 1 MiB. Docker DNS
обновляет адрес приложения в Nginx после пересоздания контейнера.

Исходники находятся на volume media в серверных UUID-каталогах. Имена
пользовательских файлов не используются как пути. Исходник fsync/rename
сохраняется перед общей транзакцией ссылки на файл, статуса processing и задания
Procrastinate. Публичного URL к volume нет. Формат и кодеки проверяются ffprobe;
Content-Type и расширение не являются проверкой содержимого.

Резерв: `2 × размер + PREVIEW_BUDGET_BYTES`; без Content-Length берётся максимум.
Проверяются учётные квоты и консервативный свободный запас физического диска.
Резерв снимается только после удаления файлов. При 429/503 учитывайте Retry-After;
507 означает место/квоту/недоступную запись. При обрыве проверьте статус перед
повтором: сервер мог успеть зафиксировать файл и задание. Повтор начинается с
первого байта и не создаёт новую карточку.

Compose запускает `upload-maintenance`, который очищает истёкшие/неудачные
попытки каждые 15 секунд. При SIGKILL/сбое БД резерв сохраняется до истечения
аренды и успешной очистки. Файловая блокировка не позволяет удалить файл живого
писателя даже после истечения аренды. Если она истекла, писатель не может
завершить загрузку. При локальном запуске нужен отдельный процесс:

```bash
uv run --locked python -m app.uploads.maintenance
# Однократная сверка:
uv run --locked python -m app.uploads.maintenance --once
```

Worker исполняет задания videos.process из video_queue. После
MAX_PENDING_VIDEO_JOBS=100 новые передачи получают 503, пока очередь не разгрузится.
Исходник успешно подготовленного видео сохраняется; неподдерживаемые и неудачные
попытки очищаются вместе с производными файлами. Удаление готового видео — этап 5.

## Обработка — этап 4

Compose запускает `worker` с FFmpeg/ffprobe, одной обработкой одновременно,
CPU=1, memory=2 GiB и pids_limit=64. Файловая система контейнера read-only,
запись разрешена в volume media и ограниченный tmpfs. Linux launcher задаёт
каждому media-процессу предел виртуальной памяти (768 MiB), CPU и размера файла;
общий таймаут обработки — 900 секунд. Child получает только минимальное окружение.
В ffprobe/FFmpeg разрешён file-протокол и MOV/MP4 demuxer, внешние data references
выключены. Неподдерживаемые кодеки не перекодируются.

Проверяются контейнер, число дорожек, H.264 8-bit yuv420p, progressive,
профиль/уровень, AAC-LC, размеры, частота кадров и длительность. Worker делает
stream-copy в MP4 с faststart, проверяет полное декодирование результата,
создаёт JPEG до 640 px и публикует пути/метаданные одной транзакцией после fsync.
Готовые файлы пока не имеют HTTP-маршрутов раздачи.

Каждый запуск получает UUID и аренду. Истёкший/старый запуск не публикует
результат, даже если процесс ещё жив. Межпроцессные файловые блокировки
ограничивают число писателей; дочерние инструменты удерживают их и завершаются
при смерти родителя. Подтверждение библиотечного задания проверяет ID worker и номер доставки,
чтобы поздний ответ старого процесса не изменил восстановленное задание.

Временные ошибки повторяются с ограниченным бюджетом; до 3 фактических media-
запусков. Ошибки профиля, декодирования и ресурсных лимитов сразу дают failed
с безопасным error_code. Уборщик возвращает зависшие задания в библиотечную
очередь, сохраняет ready при сбое до подтверждения и очищает незавершённые файлы.
Учётный резерв снимается после unlink; при ошибке удаления он сохраняется.

Для запуска без Docker нужны Linux, ffmpeg и ffprobe в PATH, применённая миграция
0006 и отдельные процессы worker/maintenance:

```bash
uv run --locked python -m app.processing.worker
# В другом терминале:
uv run --locked python -m app.uploads.maintenance
```

Настройки перечислены в `.env.example` и [политике видео](docs/video-policy.md).
Процесс может начать обработку ранее загруженных заданий сразу после запуска.

## Воспроизведение и удаление — этап 5

После загрузки дождитесь «Видео готово» и нажмите «Смотреть видео». Превью и
ссылка на просмотр также есть в «Мои видео». В карточке можно менять метаданные,
выдавать и отзывать доступ существующим аккаунтам и удалять видео с подтверждением.
Гость видит только public; private доступно владельцу и получателям grants.

Все GET/HEAD, включая Range, проходят текущую ACL. Приложение выдаёт внутренний
X-Accel-Redirect, а Nginx передаёт MP4/JPEG из volume, подключённого read-only.
Новый небольшой образ web использует UID 10001 для чтения закрытых файлов worker;
открывать доступ к каталогам всем пользователям не требуется. Прямого публичного
пути к media нет, ответы используют private/no-store. Уже полученные байты
отозвать нельзя; после отзыва или удаления новые запросы получают 404.

Полный просмотр требует Nginx: обычный `bash scripts/start.sh` собирает оба
образа и запускает весь контур. Режим uvicorn без Nginx подходит для API и
обработки, но не передаёт файловые байты. Новых миграций этап 5 не требует:
durable cleanup использует upload_attempts/processing_runs из 0005–0006.
Проверки реального HTTP и браузера описаны в [experiments/README.md](experiments/README.md).

## Управление сервисами и данными

```bash
docker compose ps
docker compose logs --tail=100 app migrate web worker upload-maintenance
docker compose stop
bash scripts/start.sh
```

Повторный запуск применяет только новые миграции. База и хранилище живут в
именованных volumes и сохраняются при пересоздании контейнеров.
Не используйте `docker compose down -v` для обычной остановки: это удалит данные.
Не меняйте пароль в `.env` уже созданной БД без отдельной смены пароля в PostgreSQL.
Согласованные encrypted backup/SSH и восстановление реализованы в
`scripts/ops.py`: [инструкция оператора](docs/deployment.md). Для production
используйте установленный `video-platform` wrapper, который подключает HTTPS overlay.

## Жалобы и модерация — этап 9

На странице доступного видео вошедший пользователь может отправить жалобу:
спам, запрещённый контент, нарушение прав или другое, с пояснением до 2000 символов.
Одна открытая жалоба на пару пользователь/видео: первая отправка возвращает 201,
повторная — 200 с прежней жалобой без изменения пояснения. После рассмотрения
допустима новая жалоба. Недоступное видео не принимает жалобы.

`/moderation` доступен moderator/admin: очередь с фильтром open/resolved/dismissed,
карточка жалобы, отдельное скрытие/восстановление и журнал с фильтром по видео.
Закрытие жалобы не меняет видимость видео автоматически. Причина решения,
скрытия и восстановления обязательна; запись действия и аудита атомарна.
Повтор того же состояния видео не переписывает причину и не добавляет событие;
ответ changed=false позволяет показать это явно и сохранить введённый текст.
Повтор решения с теми же статусом и причиной сохраняет первоначального исполнителя;
попытка изменить закрытое решение получает 409. После конфликта экран загружает
актуальное решение и сохраняет несохранённый текст отдельно. «Обновить сведения»
повторяет чтение без новой записи. Повреждённый или неполный ответ сервера не
подтверждает действие; данные проверяются до изменения экрана.

Жалоба и роль не открывают приватное видео. Сотрудник видит сведения дела,
UUID и состояния, а название и ссылку просмотра — только при обычном доступе.
Скрытие блокирует новые запросы просмотра, MP4/Range/HEAD, превью, лайков и
комментариев для всех ролей, убирает видео из каталога, канала и плейлистов.
Владелец видит причину в студии; «Проверить статус» обновляет её без перезагрузки.
Редактирование метаданных не отменяет скрытие. Восстановление сохраняет текущую
приватность и grants, не восстанавливает удалённое владельцем видео.

Лимиты на пользователя: REPORT_CREATE_LIMIT_PER_HOUR=10 и
MODERATION_WRITE_LIMIT_PER_MINUTE=120. Запись требует сессии и CSRF.
API и схемы описаны в `/docs` и [контракте](docs/api/video-contract.md).
Создание администратора через существующий CLI; публичного назначения ролей нет,
экран управления пользователями реализован на этапе 10. В аудите нет API изменения
или удаления, UUID исполнителя/объекта сохраняются независимо от их удаления.
Миграция 0010 добавляет reports/audit_events. Её downgrade удаляет историю и жалобы,
но сохраняет поля скрытия в videos; для рабочего отката необходим backup.


## Администрирование — этап 10

После создания первого администратора через CLI в меню появляется «Пользователи».
`/admin/users` позволяет искать по имени/email, фильтровать роль и открывать
следующую страницу. Карточка содержит ID, имя, email, текущую роль и форму
назначения user/moderator/admin с обязательной причиной. Только admin получает
эти данные; moderator/user не видят чужие учётные записи или историю ролей.

Смена роли учитывается уже существующей сессией при новом запросе. Регистрация
и профиль не позволяют назначить себе роль; привилегии не открывают приватные
или скрытые видео. Самопонижение требует подтверждения на экране и закрывает
управление, сохраняя вход в аккаунт. Последнего администратора понизить нельзя,
в том числе параллельными запросами. Роль исполнителя заново проверяется в
транзакции после ожидания блокировки; роль и аудит коммитятся вместе.

Список не содержит хешей паролей или сессий. История `/admin/audit` доступна
только admin и отделена от журнала модерации. Повтор уже назначенной роли не
создаёт событие и не стирает введённый текст. Устаревшее expected_role вызывает
409 role_conflict, последняя роль admin — 409 last_admin. Экран обновляет
карточку и сохраняет черновик; неполный ответ не подтверждает запись.
Совпавший с сервером выбор роли становится чистым и следует дальнейшим
обновлениям; настоящий несохранённый выбор и причина остаются.
HTTP-запросы общего JSON helper ограничены 15 секундами, включая чтение тела
ответа. При таймауте изменение не повторяется автоматически: интерфейс запрашивает
текущие сведения, сохраняя неопределённый результат и черновик. Ошибка CSRF
не закрывает панель, пока проверка сессии не подтвердила утрату прав.

Четыре API описаны в [контракте администрирования](docs/api/administration.md)
и `/docs`. Настройка ADMIN_WRITE_LIMIT_PER_MINUTE=30 ограничивает изменения на
администратора; записи требуют сессии и CSRF. Миграция 0011 добавляет только
индексы users, её downgrade не удаляет роли, пользователей или историю.
